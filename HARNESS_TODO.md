## Items

- [x] **T1**: Render timeout margin. commands/preview_render_server.go caps the local render handler at renderTimeout (5 min) while commands/preview.go sets the Studio client timeout to bannerRenderClientTimeout = renderTimeout + 30s, so the local handler's deadline always fires first and the client timeout is dead code; a Studio render that answers just under 5 minutes is cut off locally and the user gets a generic timeout instead of Studio's answer. Make the ordering explicit: the local handler's deadline is the client timeout plus a margin (named constants, comment explaining the order: Studio's own cap < client timeout < local handler deadline). Test TestRenderTimeoutsLeaveMargin in new file commands/preview_timeouts_test.go asserts that ordering, and a handler test with a fake Studio that answers after the client timeout (use small injected durations) shows the client-timeout message, not the handler's context-deadline message.
  - verified
- [x] **T2**: Render uses the row the page shows, not a CSV re-read at click time. Today a real render reads the data file again when the button is clicked, so if the CSV changed after the last fill the paid render shows different values than the preview on screen. Render from the values of the last successful fill (report.json carries "values" per row) for the row index the page sends. If the row no longer exists in that snapshot, answer with a clear Dutch error. Test TestRenderUsesTheFilledRowNotTheCurrentCSV in new file commands/preview_render_snapshot_test.go: fill, then change the CSV on disk without a refill, click render for row 0, assert the fake Studio received the filled values, not the new CSV values.
  - reopened (1): verifier: The implementation still re-reads the CSV when the snapshot row has nil Values (commands/preview_render.go:201-209). That can make a paid render differ from the displayed last successful fill, contrary to the requirement that render use the snapshot rather than a click-time CSV read. Next: Remove the CSV fallback and return a clear Dutch error when the selected snapshot row lacks Values.…
- [x] **T3**: Panic recovery. A panic in any local preview HTTP handler (page server, banner server, render handler, SSE) must not take the CLI down. Wrap the preview servers' handlers in one recover middleware: log the panic with a stack trace to stderr, answer 500 with a short Dutch message if headers were not yet written, and keep serving. Test TestPreviewHandlersRecoverFromPanic in new file commands/preview_recover_test.go: a handler that panics returns 500 and the next request on the same server still succeeds.
  - verified
- [x] **T4**: Render confirmation per template, not per port. The "a real render costs credits" confirmation is remembered in the browser's localStorage key "taufinity.preview.renderConfirmed", which is scoped to the page origin, and the origin includes the port the CLI picks on each run: so the confirmation comes back every run, and a run that happens to reuse a port inherits another folder's confirmation. Store the confirmation in the template folder's .taufinity/preview.json (preview_key.go owns that file; add a field, keep existing fields and the template key untouched) via a small local endpoint the page calls when the user confirms, and have the page read the confirmed state from the server, not from localStorage. Remove the localStorage use. Tests in new file commands/preview_confirm_test.go: TestRenderConfirmationPersistsPerTemplate (confirm, restart the server on another port for the same folder, state is confirmed) and TestRenderConfirmationIsNotSharedBetweenFolders.
  - verified
- [x] **T5**: No refill while no tab is open. The watcher refills on every save even when no browser tab is connected to the SSE stream, which spends fills (and can start a paid session) for nobody. Track the number of connected SSE clients in the server; while it is zero, a save only marks the preview stale; when a tab connects and the preview is stale, refill once. The first fill at start-up stays as it is. Tests in new file commands/preview_notab_test.go: TestWatcherDoesNotRefillWithoutAnOpenTab (save with no client: fake Studio gets no call) and TestWatcherRefillsOnceWhenATabConnects (then connect a client: exactly one call).
  - verified
- [x] **T6**: Test comment wording. In the browser test helper browserFor (commands test files), the comment that explains why WithNewBrowserContext is not used says Chrome refuses a new tab "once the first one has closed"; that is inaccurate. Replace it with: headless Chrome refuses a new tab in a fresh browser context (-32000, no browser is open). Comment only, no behaviour change.
  - verified
- [x] **T7**: Docs. Update the preview section of README.md and `taufinity preview --help` (commands/preview.go) where behaviour changed: the render confirmation is remembered per template folder in .taufinity/preview.json, and nothing is refilled while no browser tab is open.
